## What it is, when to use it, when not to

GitHub Actions runs workflows in response to repository events and other triggers. It is useful when your code already lives on GitHub and you want checks, releases, or deployments tied to pull requests and pushes.

It adds a hosted-service dependency and can incur runner and storage costs. Compare portability, security controls, and runner availability with your existing CI platform before migrating.

## Prerequisites and versions

Workflows require a GitHub repository with Actions enabled. The recorded version is the open-source runner's latest verified release, **2.338.2**; GitHub's hosted service and individual actions are versioned separately.

## Install and minimal setup

Put a workflow file under `.github/workflows` in your repository. The example uses a GitHub-hosted Linux runner, checks out the repository, sets up Node.js, and runs an existing test.

## Correct implementation

The workflow limits token permissions, disables persisted checkout credentials, cancels superseded runs, and pins each action to a full commit SHA. The Node version is explicit. The test command assumes the accompanying files exist at the displayed repository paths.

## Integrate with the rest of the stack

Run unit checks, production builds, and [browser tests](/tools/testing/playwright/) before deployment. Separate deployment credentials and environments from pull-request checks, and use caches only where the cache key and trust boundary are appropriate.

## Test it

Run `bun run snippets` in this repository to type-check and execute the same Node test command used by the example workflow. Lint the workflow with actionlint and test it in a repository before relying on it; local execution does not reproduce hosted-runner permissions or event behavior.

## Security and performance

Use least-privilege token permissions, pin third-party actions to full commit SHAs, and store credentials as protected secrets. Do not run untrusted pull-request code with privileged triggers or interpolate untrusted event data directly into shell commands. Limit unnecessary jobs and monitor usage costs.

## Common mistakes

Avoid mutable action tags for security-sensitive workflows, overly broad permissions, and assuming a successful local command proves a GitHub workflow will execute. Check runner availability and the trust boundary of any artifacts or caches.

## Observability

Review workflow status, logs, duration, and failure trends. Alert on repeated deployment or main-branch failures, and restrict access to logs and artifacts that may contain sensitive output.

## Upgrade and migration notes

Review runner and action release notes, update pinned SHAs deliberately, and exercise the workflow on a branch before relying on it for deployment. Retain the prior version of the workflow for rollback.

## Alternatives

Other hosted or self-managed CI systems may be preferable when they better match your source control, compliance needs, runner requirements, or existing operations. Keep application test commands independent of the CI vendor where possible.
