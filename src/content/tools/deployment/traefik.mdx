## What it is

Traefik Proxy is a reverse proxy and load balancer that can build routing configuration from providers such as Docker, Kubernetes, and files. It is most useful when services are created, removed, or redeployed often and routes should follow those changes without maintaining a separate static proxy configuration for every service.

Use it for dynamic container or orchestrator environments, especially when its provider integrations and middleware model reduce operational work. For a few stable sites, adding a proxy may not be worthwhile; a simpler web server or a platform-managed ingress may be easier to operate.

### How routing works

Requests enter through an entry point, match a router rule, pass through any configured middleware, and reach a service. Providers supply routing configuration; Traefik watches supported providers and updates its active configuration as their state changes.

The configuration model separates static installation settings—such as entry points and enabled providers—from dynamic routing settings—such as routers, services, middleware, and certificates.

### Traefik vs NGINX

Both can terminate TLS, proxy requests, and load-balance upstreams. The key difference is how routes are configured and updated.

**Choose Traefik** when automatic discovery saves work as services change. **Choose NGINX** when routes are stable, its web-server features matter, or it is already your team's standard. NGINX Plus is a separate commercial edition with additional capabilities.

Neither is universally faster. Benchmark your routes, TLS settings, payloads, and concurrency before choosing.

## Prerequisites and versions

This guide covers Traefik **3.7.19**. Choose an installation method and provider, decide who owns TLS and DNS, and confirm the proxy can reach only the intended upstream networks. The Traefik dashboard helps inspect active configuration; it is not a substitute for health checks, logs, or deployment tests.

## Install and minimal setup

Start with one test route, then verify the route, certificate, backend health, and behavior for an unknown host. Keep provider access scoped and store sensitive configuration outside public service labels and repositories.

## Correct implementation

- Define entry points and providers in static configuration.
- Give each router a narrow host and path rule, and set priority deliberately when rules overlap.
- Point services to reachable upstream addresses and ports.
- Configure TLS and middleware intentionally; discovering a service does not also make it safe to expose.

## Integrate with the rest of the stack

Coordinate route ownership with the platform that discovers services. This repository's [Angular + Keycloak blueprint](/blueprints/angular-keycloak-platform/) demonstrates a file-provider setup with host-based routing, an API path rule, explicit router priority, and provisioned TLS certificates. Make health checks, timeouts, and upstream behavior consistent with application expectations.

## Test it

Check intended host and path routing, TLS, redirects, middleware behavior, upstream health, and rejection of unrecognized traffic. For API routes, test boundary cases such as `/api`, `/api/`, and a similarly prefixed but unrelated path. Automated tests are intentionally omitted from this guide; use staging checks that match your deployment provider and TLS setup.

## Security and performance

Traefik warns that enabling the API and dashboard exposes configuration information. Do not expose the insecure dashboard/API port publicly; keep it on a private management network or route it through authentication and authorization. Scope provider permissions—for example, access to the Docker socket can grant substantial control of the host.

Set resource and connection limits appropriate to the workload. Benchmark representative routes, TLS settings, payload sizes, and concurrency before drawing performance conclusions.

## Common mistakes

- Exposing the dashboard or API without access controls.
- Depending on container metadata from untrusted workloads to publish public routes.
- Using catch-all rules or overlapping routers without verifying precedence.
- Treating a successful proxy startup as proof that certificates, upstream health, or fail-closed behavior are correct.
- Adding Traefik to a static deployment without a concrete need for its provider model.

## Observability

Monitor request status and latency, backend health, certificate renewal, and proxy errors. Keep dashboard access private and redact sensitive data from diagnostic output.

## Upgrade and migration notes

Review Traefik's release notes and provider-specific changes before upgrading. Validate routes and TLS in staging before rolling out; the exact integration depends on the selected provider and deployment platform.

## Alternatives

Caddy emphasizes straightforward web serving and HTTPS; NGINX Open Source provides a mature web server and explicit proxy configuration; platform-native ingress may be preferable when already standardized. Prefer the one that best fits your route-change frequency, feature requirements, and existing operations skills.
