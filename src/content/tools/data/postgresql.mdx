## What it is, when to use it, when not to

PostgreSQL is an open-source relational database with transactions and a rich SQL feature set. Use it when your application benefits from relational constraints, consistent updates, and operational control over data.

It still requires capacity planning, backups, upgrades, and access controls. A lightweight local store or a managed service may be preferable when those operational responsibilities are disproportionate to the application.

## Prerequisites and versions

The latest stable PostgreSQL release verified for this guide is **18.7**. The runnable example uses an in-memory PGlite PostgreSQL build for fast isolated SQL checks; it does not start or validate a PostgreSQL 18.7 server.

## Install and minimal setup

Install a supported PostgreSQL distribution or provision a managed instance using its provider's instructions. Create a dedicated database and least-privilege application role, and keep connection credentials outside source control. Apply versioned migrations through your deployment process.

## Integrate with the rest of the stack

Run migrations before application versions that depend on the new schema, while planning compatibility between deployments. Size connection pools for the database and application replicas, and use secure transport when connections leave a trusted local environment.

## Test it

Run `bun run snippets` in this repository. The example applies the migration to PGlite and tests parameter binding and rollback. Also run integration tests against a real PostgreSQL server: the embedded test does not verify server networking, roles, extensions, backups, or deployment behavior.

## Security and performance

Grant only necessary database privileges, protect credentials, use parameterized queries, and avoid logging sensitive values. Review indexes and query plans for real workloads. Maintain backups and regularly test restores; a successful backup job alone does not demonstrate recoverability.

## Common mistakes

Avoid building SQL by concatenating untrusted values, leaving long transactions open, or relying on migrations that were never tested against production-like data. Do not treat an embedded database test as a replacement for server-level tests.

## Observability

Monitor connection utilization, query latency, errors, storage, replication lag where applicable, and backup and restore outcomes. PostgreSQL's statistics views provide operational signals; alert on user-visible degradation as well as resource exhaustion.

## Upgrade and migration notes

Read the exact release notes and test upgrades and restores on a representative copy before production. PostgreSQL 18.7's notes call out cases requiring index review and recommend a new full backup for incremental-backup users; follow the release guidance for your installation.

## Alternatives

SQLite is useful for embedded and simpler single-process workloads. A managed relational service may reduce operational work, but compare its version support, recovery guarantees, portability, and pricing.
