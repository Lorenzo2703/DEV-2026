## What it is, when to use it, when not to

pnpm is a package manager for JavaScript projects, with workspace support and a lockfile-based install workflow. Use it when its dependency model and workspace features fit your team and deployment pipeline.

Prefer the package manager already chosen for a repository unless there is a concrete reason to migrate. This handbook uses Bun; this guide shows a separate pnpm workspace so its lockfile and commands remain isolated from the site.

## Prerequisites and versions

This guide is verified against **pnpm 12.18.0**, the latest stable release found on 2026-11-12. pnpm 12 is distributed as a native executable; installing the `pnpm` npm package requires Node.js 18 or newer. The example repository uses Node.js 22.23.4 and pins pnpm with `packageManager`.

## Install and minimal setup

For a Node.js-based setup, install the pinned release and confirm the executable:

```sh
npm install --global pnpm@12.18.0
pnpm --version
```

In a repository, commit `package.json`, `pnpm-workspace.yaml`, and `pnpm-lock.yaml` together. The example below has no registry dependencies, so the workspace behavior can be tested without downloading third-party packages.

## Correct implementation

Pin the package manager version in the root manifest and declare the workspace patterns in `pnpm-workspace.yaml`. Use the `workspace:` protocol when a package must resolve to a local workspace member; it makes a missing local package an install error rather than silently selecting a registry package.

Commit the generated lockfile. In CI, request a frozen install explicitly with `pnpm install --frozen-lockfile`; do not rely solely on automatic CI detection. Keep the pnpm major that wrote the lockfile aligned with the one used by CI, since incompatible lockfiles fail rather than being silently rewritten.

For larger workspaces, keep package boundaries explicit and use the workspace protocol for internal dependencies. Add pnpm configuration in `pnpm-workspace.yaml`, not an invented `pnpm` section in `package.json`.

## Integrate with the rest of the stack

Pair pnpm with a runtime/version manager such as [mise](/tools/package-management/mise/) when the project needs the same Node.js and package-manager versions across local development and CI. The [Bun guide](/tools/package-management/bun/) describes this site's selected package manager; don't mix lockfiles in one project without an explicit migration plan.

## Security and performance

pnpm restricts dependency build scripts unless they are explicitly allowed. Review packages that need install-time execution and allow only the ones you trust. Keep registry credentials out of committed configuration and logs.

Set a deliberate policy for dependency update age and trust, and consider `minimumReleaseAge` or `trustPolicy` where they fit your threat model. Do not share pnpm's store or metadata cache from an untrusted job with trusted CI jobs. If security scanners read the lockfile, make sure they support pnpm's possible two-document format; reading only the first document can miss the project dependency graph.

Measure install time in the actual CI environment. A warm store is not guaranteed to make every pipeline faster.

## Common mistakes

- **Omitting the version pin:** local and CI machines can run different pnpm versions. Pin one exact version with `packageManager`.
- **Treating a lockfile as a substitute for a frozen install:** use the explicit CI flag so dependency drift fails visibly.
- **Using `workspaces` in `package.json` without `pnpm-workspace.yaml`:** pnpm reads its workspace patterns from the YAML file.
- **Declaring an internal dependency with a normal version range:** use `workspace:` when the dependency must come from the local repository.
- **Assuming the lockfile is always one YAML document:** scanners and SBOM tools must read the format pnpm actually generated.
- **Approving every dependency build script:** this removes a useful supply-chain boundary; allow only reviewed packages.

## Observability

Keep install output in CI logs and track install duration and failures alongside the lockfile revision and pnpm version. Investigate lockfile changes and rejected build scripts during dependency updates; avoid logging registry credentials or environment secrets.

## Upgrade and migration notes

Update the exact `packageManager` pin deliberately, regenerate the lockfile using that version, and review the diff before merging. Then run the same frozen install in CI. Read the release notes before changing major versions; pnpm 12 is a native executable, and its installation and Node.js requirements differ from older JavaScript-based pnpm releases.

To leave pnpm, migrate the lockfile and workspace declarations intentionally. Do not commit multiple competing lockfiles as if they were interchangeable.

## Alternatives

Bun is this handbook's choice and combines package management with a runtime and test runner. npm is a practical default for Node.js-centered projects; Yarn is another established option. Compare workspace behavior, lockfile support, platform needs, and CI integration before switching.
